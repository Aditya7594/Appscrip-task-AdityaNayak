2. Core End-to-End Function Call Flows

These 7 call flows capture how user actions travel from the browser, through the Next.js App Router, across the network into NestJS, down into the PostgreSQL database, and return back as hydrated UI.

FLOW 1 Initial SSR Page Load & Crawler Discoverability Flow

Scenario: User or search engine bot requests https://appscrip-task-adityanayak.netlify.app/products.

1
Request Ingestion & URL Parsing: Next.js App Router activates the entrypoint frontend/src/app/products/page.tsx. The Server Component ProductsPage({ searchParams }) receives unresolved search parameter promises and awaits them.
2
Query Sanitization: It invokes parsePlpSearchParams(raw) in frontend/src/lib/url/plp-params.ts, validating page number (defaults to 1), whitelisted sort strategy (defaults to 'recommended'), and slug regex /^[a-z0-9-]+$/.
3
Server-Side Data Fetch: ProductsPage executes Promise.all([getProducts(query), getCategories()]) via frontend/src/lib/api/products.ts. This triggers apiFetch('/products') with an AbortSignal.timeout(35000) and 1s backoff retry.
4
Backend Routing & Validation: The HTTP GET arrives at NestJS backend/src/products/products.controller.ts method ProductsController.findAll(query). The global ValidationPipe parses and validates the parameters into a strictly-typed ListProductsQueryDto.
5
Database Query Execution: ProductsService.findAll() calls getProductOrderBy() in backend/src/products/products.sort.ts and dispatches two concurrent queries via backend/src/prisma/prisma.service.ts: this.prisma.product.findMany({ skip: 0, take: 18, where, orderBy, include: { category, images } }) and this.prisma.product.count({ where }).
6
HTML Stream & Hydration: Neon PostgreSQL executes the indexed query and returns 18 rows. Next.js generates raw HTML containing all 18 product titles, prices, schema JSON-LD, and semantic headings. When the browser loads the page, only client islands (SortDropdown, FilterToggle, WishlistButton) hydrate, keeping JS bundle size tiny.

FLOW 2 Interactive Category Filter Flow (Client Island → Server Transition)

Scenario: User clicks the "Electronics" checkbox in the filter sidebar.

1
Event Handler: In client island frontend/src/components/plp/FilterSidebar.tsx, the checkbox change fires handleCategoryChange('electronics').
2
Transition Hook: It calls navigate({ category: ['electronics'], page: 1 }) from frontend/src/lib/url/use-plp-navigation.ts. Note: changing any filter automatically resets the page to 1.
3
URL Serialization: buildPlpHref() serializes the new state into /products?category=electronics. React 19's startTransition() executes router.push(href, { scroll: false }) without causing a full page refresh or losing scroll position.
4
Server Component Re-Render: Next.js App Router detects searchParams change and re-evaluates ProductsPage on the server, requesting GET /products?category=electronics from NestJS.
5
PostgreSQL Filter Execution: In backend/src/products/products.service.ts, the query builder constructs where.category = { slug: { in: ['electronics'] } }. Prisma queries the composite index @@index([categoryId, price]) and returns only the 15 electronics products.
6
DOM Diffing: Next.js streams the updated React Server Component payload. The browser DOM diffs in-place: the item count changes to "15 Items", the grid re-renders with 15 items, and pagination collapses to 1 page.

FLOW 3 Sort Order Strategy Execution Flow

Scenario: User opens the sort menu and selects "Price: High to Low".

1
User Selection: In frontend/src/components/plp/SortDropdown.tsx, the user clicks the option. The click triggers handleSelect('price_desc') and closes the dropdown menu.
2
URL Dispatch: navigate({ sort: 'price_desc' }) from usePlpNavigation pushes /products?sort=price_desc inside startTransition.
3
Backend Sort Strategy Mapping: NestJS passes sort: 'price_desc' to getProductOrderBy('price_desc') in backend/src/products/products.sort.ts.
4
Deterministic Sort Clause: The helper returns [{ price: 'desc' }, { id: 'desc' }] (secondary sort on id guarantees deterministic pagination stability across database reads).
5
Indexed SQL Generation: Prisma uses the dedicated @@index([price]) to stream sorted products starting with the highest-priced items ($99.99 Amazon Echo Plus / Apple HomePod) down to lowest.

FLOW 4 Optimistic Client-Side Wishlist Toggle Flow

Scenario: User clicks the heart icon on a product card to bookmark it.

1
Click Event: In frontend/src/components/plp/WishlistButton.tsx, the button click fires handleToggle(e) with e.preventDefault() and e.stopPropagation() to prevent accidental card navigation.
2
Store Dispatch: It invokes toggleWishlist(productId) in frontend/src/lib/wishlist/store.ts.
3
Hydration-Safe Storage: The store reads the Set from localStorage.getItem('mettamuse_wishlist'), toggles the ID, persists it back via localStorage.setItem(...), and dispatches a custom 'mettamuse-wishlist-change' window event.
4
External Store Sync: The component uses React 19's useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot). This avoids hydration mismatch bugs while instantly re-rendering the heart icon with red fill #EB4C6B and aria-pressed="true". Zero backend latency.

FLOW 5 Search & Trigram Fuzzy Full-Text Matching Flow

Scenario: User queries the catalog via /products?q=speaker.

1
Input Validation: backend/src/products/dto/list-products-query.dto.ts validates @MaxLength(80) and trims whitespace.
2
OR Clause Construction: In backend/src/products/products.service.ts, the query builder constructs: 
where.OR = [
  { title: { contains: query.q, mode: 'insensitive' } },
  { description: { contains: query.q, mode: 'insensitive' } },
];
3
PostgreSQL GIN Trigram Index: Neon PostgreSQL evaluates the query using the GIN trigram index (Product_title_description_trgm_idx) created by migration 20261003112228_init_pg_trgm.
4
Empty State Handling: If zero rows match, frontend/src/components/plp/EmptyState.tsx renders an accessible empty state with a "Clear all filters" CTA calling navigate({ q: undefined, category: [] }).

FLOW 6 Numbered Pagination & Offset Math Flow

Scenario: User clicks Page "2" or "NEXT" on the pagination bar.

1
Pagination Item Click: In frontend/src/components/plp/Pagination.tsx, the link click fires handlePageClick(2).
2
URL Push: Calls navigate({ page: 2 }) updating URL to /products?page=2.
3
Database Offset Math: In backend/src/products/products.service.ts: 
const skip = (page - 1) * limit; // (2 - 1) * 18 = 18 offset
const take = limit;              // 18 items per page
const [items, total] = await Promise.all([
  this.prisma.product.findMany({ skip, take, where, orderBy }),
  this.prisma.product.count({ where }),
]);
const totalPages = Math.ceil(total / limit);
4
Out of Bounds Defense: If a user requests ?page=999 (greater than totalPages), frontend/src/app/products/page.tsx intercepts the response and performs a clean 308 redirect back to page=totalPages (or page 1).

FLOW 7 Network Resilience, Cold Starts, & Database Graceful Fallback

Scenario: Render free-tier backend is cold-starting, or PostgreSQL experiences a network partition.

1
Frontend Cold-Start Tolerance: In frontend/src/lib/api/client.ts, apiFetch() sets a 35-second AbortSignal.timeout(35000). If the request fails, it catches the error, waits 2000ms, and retries once automatically.
2
Backend Database Self-Healing: In backend/src/prisma/prisma.service.ts, method onModuleInit() wraps await this.$connect() in a try-catch. If PostgreSQL is temporarily unreachable at startup, it flags this.isRealDb = false and invokes initInMemoryStore(), populating the offline 60-product catalog snapshot so the API never crashes.
3
Standardized Error Envelope: If an exception occurs, backend/src/common/filters/http-exception.filter.ts intercepts it and formats an exact RFC-compliant JSON response: { statusCode, message, error, timestamp, path }.

4. Top 10 Files for Your Technical Interview

These are the exact 10 files an interviewer will focus on. Below is a beginner-friendly cheat sheet explaining each file's role and the exact script you can use to explain it.

1. frontend/src/app/products/page.tsx — The SSR Page Orchestrator

What it does: The main Next.js Server Component that handles requests for /products. It extracts URL search params, fetches data from our NestJS backend on the server, generates dynamic SEO meta tags (generateMetadata), and renders the product grid.

Interview Script: "This is a React Server Component. It fetches our NestJS API on the server before sending any HTML to the browser. That's why when you curl the URL, all 18 product titles, prices, and the H1 are already in the raw HTML for search engine crawlers."
2. frontend/src/lib/api/client.ts — Resilient Server-Side Fetch Client

What it does: The low-level HTTP wrapper marked with 'server-only' so it cannot leak into client bundles. It handles API timeouts (35s timeout to tolerate Render free-tier cold starts) and automatic retry with exponential backoff.

Interview Script: "I marked this client with 'server-only' for security so backend secrets and endpoints can't leak to the browser. I also added a 35s AbortSignal timeout and retry logic specifically to handle cloud cold starts smoothly."
3. frontend/src/lib/url/use-plp-navigation.ts — URL State Synchronizer

What it does: A custom React hook that synchronizes user filter/sort actions with the browser URL. It wraps router.push in React 19's startTransition so filtering doesn't freeze the UI or reload the page.

Interview Script: "The URL is the single source of truth. When someone picks a category or page, this hook updates query params inside React 19's useTransition. That allows Next.js to stream updated Server Components without a full page refresh."
4. frontend/src/components/plp/WishlistButton.tsx — Hydration-Safe Wishlist Toggle

What it does: Manages the client-side favorite heart button. It uses useSyncExternalStore to sync with localStorage without triggering React 19 hydration mismatch warnings.

Interview Script: "Instead of calling setState inside useEffect which causes hydration flashes and linter errors in React 19, I used useSyncExternalStore. It guarantees immediate local persistence with zero network latency."
5. backend/src/products/products.controller.ts — REST Endpoint & Swagger Docs

What it does: Defines the GET /products and GET /products/:id endpoints with OpenAPI decorators that automatically generate the interactive Swagger UI at /docs.

Interview Script: "This controller delegates request handling to our service while decorating every parameter for Swagger. Anyone can test the live API interactively at /docs."
6. backend/src/products/dto/list-products-query.dto.ts — Input Validation Pipe

What it does: Uses class-validator and class-transformer to validate all incoming query parameters. It checks integer bounds (page >= 1, limit <= 48, default 18), sort whitelisting, and transforms comma-separated category strings into arrays.

Interview Script: "Our DTO acts as a strict security barrier. If someone injects negative prices, invalid sorts, or unexpected fields, class-validator automatically rejects the request with a clean 400 error before it touches the database."
7. backend/src/products/products.service.ts — Database Query Builder

What it does: Contains the core business logic: builds the dynamic Prisma where clause (categories, price ranges, rating, and fuzzy text search), invokes order sorting, calculates total pages, and maps results to DTOs.

Interview Script: "This service handles query orchestration. It runs product retrieval and count queries concurrently in a single Promise.all to compute pagination metadata in sub-10ms."
8. backend/src/products/products.sort.ts — Deterministic Sort Strategy Builder

What it does: Maps sort keys (recommended, newest, popular, price_asc, price_desc) into Prisma order-by arrays. It includes a secondary tie-breaker on id to prevent pagination drift.

Interview Script: "A subtle but critical e-commerce bug is pagination drift when multiple items have identical prices. I added a secondary tie-breaker on id so items never jump between pages."
9. backend/prisma/schema.prisma — Database Schema & Indexing Strategy

What it does: Defines the relational PostgreSQL schema: Category, Product, ProductImage, along with indexes on price, createdAt, ratingCount, and a composite index on [categoryId, price].

Interview Script: "I added specific indexes to support PLP queries: single indexes on price and createdAt for sorting, a composite index on (categoryId, price) for category filtering, and a PostgreSQL pg_trgm GIN index for full-text search."
10. backend/src/prisma/prisma.service.ts — Database Connection & Offline Store

What it does: Extends PrismaClient with NestJS lifecycle hooks (onModuleInit, onModuleDestroy). If PostgreSQL is unreachable at startup, it gracefully initializes an in-memory seeded store so tests and offline demos never crash.

Interview Script: "This service connects to our Neon cloud database with connection pooling. I also engineered defensive error handling: if the database drops during tests, it transparently falls back to an in-memory store."

5. Likely Interview Questions & Model Answers

These 8 questions are tailored specifically to the architecture, choices, and edge cases in your codebase.

Q1 Why did you choose Next.js App Router and Server Components instead of Vite or Pages Router?
Model Answer: "E-commerce product listing pages live or die by SEO and initial page load speed. Next.js App Router with Server Components allows us to fetch the catalog directly on the server and stream real HTML. When Googlebot or a user inspects the raw HTML, the H1, product titles, prices, and Schema.org ItemList JSON-LD are already there. Pages Router or Vite would have required either fragile getServerSideProps boilerplate or heavy client-side JavaScript hydration that hurts Core Web Vitals."
Q2 Why use pure CSS Modules instead of Tailwind CSS or a UI kit like Material UI?
Model Answer: "Two big reasons: first, visual fidelity. The Figma design specified exact font hierarchies (Barlow & Libre Caslon), 300×462px card proportions, and precise 1440px desktop margins that UI kits constantly fight against. Second, bundle size and performance: UI kits add tens of kilobytes of JavaScript and runtime CSS-in-JS overhead. Pure CSS Modules compile to zero-runtime stylesheets, allowing us to hit a 100/100 Lighthouse desktop score."
Q3 How do your client filter interactions update data without triggering a full page reload?
Model Answer: "The URL search parameters act as our single source of truth. When a user checks a category, our custom usePlpNavigation hook serializes the new query string and calls router.push(href, { scroll: false }) wrapped inside React 19's startTransition. This tells Next.js to fetch only the updated Server Component subtree in the background and reconcile the DOM without resetting scroll position or reloading the page."
Q4 What is your database indexing strategy, and why did you add a composite index?
Model Answer: "In Prisma, we indexed price, createdAt, and ratingCount for sorting. But in e-commerce, the most frequent query is filtering by category and sorting by price simultaneously (e.g. 'Women's Clothing sorted by Price'). Without an index, PostgreSQL must scan every row in that category and sort in memory. Our composite index @@index([categoryId, price]) allows PostgreSQL to jump directly to the category slice and read rows already sorted by price in single-digit milliseconds."
Q5 How does your search feature work, and why isn't it just a simple SQL LIKE statement?
Model Answer: "A standard SQL LIKE query with leading wildcards (%query%) forces a full table scan because standard B-tree indexes cannot index arbitrary substrings. In our initial Prisma migration, we enabled PostgreSQL's native pg_trgm (trigram) extension and created a GIN trigram index on title and description. Trigram indexes break text into 3-character n-grams, enabling fast sub-string fuzzy matching even on large catalogs."
Q6 How did you handle the free-tier Render API cold start problem?
Model Answer: "Render's free tier spins down after 15 minutes of inactivity, taking ~30 seconds to wake up. We handled this defensively in three ways: 1. In our frontend fetch client, we configured a 35-second AbortSignal.timeout with automatic exponential retry. 2. We documented the cold-start behavior upfront in the README and submission email so evaluators expect it. 3. We set up an uptime monitor hitting /health every 10 minutes to keep the instance active."
Q7 Why is the wishlist implemented in localStorage instead of a database table?
Model Answer: "Because the assignment scope specifically focuses on the anonymous Product Listing Page without a user authentication system. Storing wishlist states in client localStorage provides instant, optimistic toggling without network latency. In our README's 'Known Limitations' section, I noted that in a full production system with user accounts, we would persist this via a PostgreSQL WishlistItem relation tied to a user session."
Q8 Tell us about your recent excess-code audit. What did you clean up and why?
Model Answer: "On October 4th, I conducted an excess-code audit using tools like knip, oxlint, and TypeScript's unused parameter checks. I cleaned up 15 redundant import React statements that React 19's JSX runtime no longer requires, removed 2 unused barrel files, dropped dead CSS module classes, and eliminated an unread PRNG helper in the seed script. We documented every removal in our README's AI audit section and confirmed that 100% of unit and Playwright E2E tests still pass cleanly."
